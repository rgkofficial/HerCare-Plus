HerCare+ — Complete Medical History & Desktop-First Redesign
HerCare+ — Complete Medical History & Desktop-First Redesign Repository: https://github.com/mohitraj8503/HerCare-Plus

Objective: Upgrade HerCare+ into a complete, privacy-first women's healthcare application with a structured Medical History module, a secure medical document vault, and a properly responsive desktop-first interface while preserving all existing functionality. Do not merely produce a plan or mockup. Inspect the existing implementation, make the changes in the working repository, run available checks, and report actual results.

Audit before implementation Inspect: src/app/medical-records/page.tsx src/app/api/medical-records/ docs/MEDICAL_RECORDS_API.md tests/medical-records.test.ts src/app/layout.tsx src/components/Navbar.tsx src/components/BottomNav.tsx src/app/globals.css Existing authentication, Supabase configuration, retention handling and security utilities. Reuse existing working functionality instead of creating duplicate APIs or incompatible database models. Verify which database tables and storage migrations already exist.

Build a complete Medical History module Create a polished /medical-records experience with the following sections: A. Health Overview Dynamic counts of documents, conditions and current medications. Most recent medical activity. Quick actions to add medical information or upload a document. Helpful empty states for new users. B. Personal Medical Profile Optional blood group, allergies, chronic conditions, past surgeries and relevant family medical history. Emergency contact. Explicitly optional women's health fields for cycle-related information, gynecological history and pregnancy history where relevant. Allow users to add, edit and remove entries. Distinguish user-reported information from clinician-confirmed diagnoses. Never require users to disclose sensitive information unnecessarily. C. Medication Management Medication name, dosage, frequency, start date, end date and optional prescribing clinician. Current, completed and discontinued statuses. Edit, discontinue and delete actions. Do not prescribe medication or invent dosages. D. Medical Documents Vault Secure uploads for PDF, JPEG and PNG files. Drag-and-drop upload, progress state, file validation and clear error messages. Categories: prescriptions, lab reports, imaging/ultrasound, discharge summaries, consultation notes, women's health reports, vaccination records and other. Search, filtering, sorting and pagination. Document preview, download, deletion and version history. Display filename, category, size, upload date and available actions. Make selected files and their metadata easy to distinguish. Ensure empty, loading, success and failure states are complete. Preserve existing API compatibility where possible. E. Medical Timeline Chronological entries for visits, uploaded reports, medication changes and user-recorded health events. Add/edit medical visits with date, provider, visit reason, notes and optional follow-up date. Use dates from saved data, never fabricated sample data. F. Export and Privacy Provide a user-initiated export of structured history and document metadata, and allow original files to be downloaded. Make clear what is included in an export. Support deletion and a transparent retention policy. Never expose private storage paths, service-role keys or permanent public document URLs.

Data architecture Use the repository's existing Next.js 14, TypeScript, Supabase and NextAuth setup. Reuse medical_records and medical_record_audit_logs after inspecting their schemas. Add suitable migrations for structured data, such as: medical_profiles medical_medications medical_visits Use stable IDs, timestamps, proper relationships and database constraints. Add indexes for owner ID, category and timeline dates as appropriate. Every private record must be scoped to the authenticated session's server-derived user ID. Never trust a client-provided owner ID. Enforce ownership for every read, insert, update, delete, preview, download, version-history and export operation. Keep sensitive records out of analytics, console logs, URLs and client-side error messages. Inspect all existing encryption claims before reusing the encryption helper. Do not treat a public identifier as a secure encryption key. Choose a documented, viable key-management design and do not break existing user data. Medical documents must remain in private storage with short-lived signed URLs. Verify file signatures, size limits, content types and safe response headers. Add a malware-scanning/quarantine integration or clearly document the unmet infrastructure dependency rather than claiming files are malware-free. Implement safe cleanup for failed uploads and failed deletions. A seven-year retention timestamp does not constitute a retention policy without an actual enforcement workflow. Do not send medical documents to an AI service without explicit informed consent. OCR/extraction must be optional, show uncertainty and require user review before saving extracted information into structured records.

Desktop-first design The current global .page-container and navigation constrain the application to approximately 480px. Refactor the overall layout so the app uses the available desktop viewport while retaining the current mobile experience. Desktop

requirements
Responsive sidebar and top header. Main content with sensible maximum widths and consistent spacing. Multi-column overview cards. Readable document tables/list views and a useful details panel. Consistent typography, spacing, controls, borders and accessible focus states. Keyboard-accessible dialogs, upload controls and menus. No horizontal overflow, clipped forms or oversized empty gaps. At smaller breakpoints: Collapse the sidebar into appropriate compact navigation. Preserve mobile navigation and touch targets. Support tablet and mobile layouts without duplicating the application's business logic. Use the existing Tailwind and Lucide dependencies. Prefer reusable components and shared design tokens over page-specific inline styles. Keep the existing HerCare+ identity and its calm, supportive women's-health aesthetic. Audit and update the navbar and bottom navigation so Medical History is discoverable without overcrowding mobile navigation. Ensure all navigation links lead to real working pages.

Security, correctness and regression testing Expand tests for: Structured CRUD and validation. Authentication failures and cross-user access denial. File signature validation, invalid types and file-size boundaries. Storage/database partial failures. Signed URL authorization and expiration assumptions. Version-history integrity. Export privacy and account deletion. Empty, error and loading UI states. Run the existing test suite, lint and production build. Fix failures introduced by your changes and investigate existing failures separately. Do not claim success unless the commands actually pass. Check representative viewport sizes: 375px, 768px, 1280px, 1440px and 1920px. If browser-based visual testing is unavailable, state that limitation honestly.

Acceptance criteria A user can create and edit a structured medical history. Uploads persist and reappear after refreshing. Records are isolated to their authenticated owner. Users can view, filter, preview, download and delete documents safely. Medical visits and medications appear in their correct sections and on the timeline. Empty states are useful and do not display fabricated personal records. Existing cycle tracking, symptom checker, care finder, authentication and PWA functionality continue working. Desktop uses the available screen width appropriately; mobile remains usable. Database migration instructions and environment requirements are documented. A final implementation report lists changed files, migrations, security limitations and actual test/build results. Prioritize data integrity and privacy over cosmetic polish. Do not rewrite the entire application unnecessarily and do not silently replace the existing authentication or storage architecture.
